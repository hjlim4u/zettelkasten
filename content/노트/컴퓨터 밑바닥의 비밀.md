##### 여러분이 프로그래밍 언어를 발명한다면
- 기계어와 해당 특정 작업을 간단하게 대응시켜 기계어를 인간이 읽고 이해할 수 있는 단어와 대응한 어셈블리어
	- 인간이 인식할 수 있는 기계 명령어를 CPU가 인식할 수 있는 0과 1로 구성된 바이너리로 변환하는 프로그램 사용
- 인간의 추상적인 표현을 CPU가 이해할 수 있는 구체적인 구현으로 자동으로 변환할 수 있는 방법
	- 명령어의 규칙
		- 조건문 / 반복문 / 함수
- 규칙 안에 선언된 명령은 그 자체로 규칙이 될 수 있어: 재귀적으로 정의(구문)
```
if: if expr statement else statement
for: while expr statment
statement: if | for | statement
```
- 재귀적으로 구성된 트리를 사용해 재귀적으로 정의된 구문을 표현할 수 있어
- 각각 다른 명령어 집합을 가진  CPU 간의 호환성
	- 통용과 표준: 직접 표준 명령어 집합을 정의해서 CPU의 기계 명령어 실행 과정을 모방하는 프로그램(가상머신, 인터프리터)을 작성하여 사용
- 컴파일러: 코드 구문 -> 구문 트리 -> 기계어(C/C++) / 바이트코드(JAVA) -> 가상머신(JAVA) ->CPU
##### 컴파일러는 어떻게 작동하는 것일까?
- 컴파일러: 소스코드 -> 기계어 번역 프로그램
- 구문 분석
	- 어휘 추출: 토큰(의미를 가진 항목 + 항목에 대한 추가 정보) 추출 (ex. int  +  키워드 여부, int 키워드 종류)
	```
	T_Keyword int
	T_Identifier a
	T_assign =
	```
	- 해석: 올바른 규칙에 따라 작성되었는지 확인(while 키워드 다음에 (조건문){처리문} ) -> 구문 트리로 표현
	```csharp
while_stmt
├── while_keyword ("while")
├── condition
│   ├── left_operand (변수 "a")
│   ├── operator ("<")
│   └── right_operand (변수 "b")
└── body
    └── statement_list
        └── assignment_stmt
            ├── variable (변수 "b")
            ├── assignment_operator ("=")
            └── expression
                ├── left_operand (변수 "b")
                ├── operator ("+")
                └── right_operand (숫자 "1")
	```
	
- 의미 분석: 생성된 구문 트리 이상 유무 판단(값 형식, 피연산자 값 확인), 완료 시 컴파일 에러 X
- 중간 코드: 최적화 진행 가능(순환 상태 관계없는 값 -> 순한 구문 외부로 이동)
	``` 
	a = 1
	b = 2
	goto B
	A: b = b - 1
	B: if a < b goto A
	```
- 코드 생성: 중간코드 -> 어셈블리어 -> 기계어로 변환

##### 링커의 말할 수 없는 비밀
- 링커: 컴파일러가 생성한 대상 파일(object file) -> 실행 파일(exe, elf)
	- 심벌 해석: 참조하고 있는 외부 심벌이 단 하나만 존재하는지, 종속성이 올바르게 설정되었는지(종속된 모듈의 인터페이스 구현체 사용 가능 여부) 확인 후 연결
	- 실행 파일 생성
	- 재배치: 컴파일 시점에 설정된 임의의 주소 -> 실제 메모리 주소로 대체
- 심벌: 전역 변수, 함수의 이름을 포함하는 모든 변수 이름
- 컴파일러 생성 대상 파일
	- 코드 영역: 소스파일에 정의된 함수에서 변환된 기계 명령어
	- 데이터 영역: 소스 파일의 전역변수(지역변수는 스택에 생성 후 제거) 저장된 영역
	- 심벌 테이블: 참조하는 심벌, 다른 모듈에서 사용하도록 정의한 심벌 기록
- 정적 라이브러리
	- 소스파일 여러 개를 미리 개별적으로 컴파일하고 링크하여 생성
	- 정적 링크 : 이후 실행 파일 생성시 자신의 코드만 컴파일, 미리 완료된 정적 라이브러리는 컴파일 없이 링크 과정에서 실행 파일에 그대로 복제
	- 실행 파일에도 코드/데이터 영역 존재, 특수 심벌 \_start가 있어 CPU가 심벌 주소에서 프로그램 실행하는데 필요한 기계 명령어 실행
	- 라이브러리를 실행 파일에 직접 복사 -> 데이터 중복 및 종속성(라이브러리 변경 시 종속된 프로그램 역시 매번 컴파일 필요)
- 동적 라이브러리
	- 정적 라이브러리: 코드와 데이터 영역을 모두 한 데 묶어 실행 파일에 복사
	- 동적 라이브러리:  참조된 라이브러리 이름, 심벌 테이블, 재배치 정보 등 필수 정보만 실행 파일에 포함
	- 동적 링크
		- 적재 도구에 의해 프로그램이 메모리에 적재 될 때, 적재 도구는 동적 라이브러리 의존 여부 확인
			- 동적 라이브러리 존재 시, 동적 링커라는 별도의 프로세스 실행(라이브러리 및 심벌 메모리 위치 확인 후 링크)
			- 실행 파일 생성 시 컴파일러에게 참조 라이브러리 명시: gcc -o pro main.c /path/libfoo.so 
		- 프로그램 실행 시간 동안 동적 링크 실행
			- 링크 과정을 프로그램 실행 시점으로 미룸(실행파일 생성 시점에서 동적 라이브러리 정보 적재 X)
			- 특정 API(dlopen/close/sym)로 동적으로 적재
	- 의존하는 프로그램 개수 상관없이 디스크에 복사본 하나만 저장, 메모리에 하나의 코드만 저장
	- 동적 라이브러리 코드 수정 시 해당 라이브러리만 다시 컴파일
	- 동적 라이브러리 방식을 따라 플러그인을 적재하여 프로그램에 새로운 기능 확장
	- 실행 시간 혹은 적재되는 시간에 링크 생성되기에 성능상의 약간의 이슈
	- 동적 라이브러리는 메모리 주소와 독립적으로 동작하는 위치 독립 코드이기 때문에 임의의 메모리 절대 주소로 참조 불가(주소 독립적 설계)
```bash
ldd helloworld (실행 파일명) //실행 파일이 의존하는 동적 라이브러리 확인 가능
```

- 컴파일 시점에는 접근하는 함수나 변수의 메모리 주소 결정 X (특정 기호0x00 로 대체)
- 대상파일 생성 시 .relo.text(해당 명령어: ex. 실행 파일 코드 영역 시작 주소 기준 60바이트 오프셋에서 심볼 발견), .relo.data(명령어 관련 데이터) 저장
- 심벌 해석
- 대상 파일에서 동일한 유형의 영역끼리 병합: 모든 기계 명령어와 전역변수가 프로그램 실행 시간에 위차할 메모리 주소 결정
- 재배치: 링커는 각 대상파일의 .relo.txt 영역을 하나씩 읽어 실행파일에서 수정해야될 명령어의 위치 확인 후 주소 수정

	- 가상 메모리 공간 기준 접근 주소 결정
	- 페이지 테이블 : 페이지 단위로 물리 메모리와 가상 메모리 간의 매핑 관계 유지

##### 운영체제, 프로세스, 스레드의 근본 이해하기
- CPU의 명령어 실행 과정
	1. PC 레지스터에 저장된 메모리 주소에서 명령어를 하나 가져옴(dispatch)
	2. 명령어 실행 후 1번 수행
- 기본적으로  PC 레지스터가 저장하는 주소는 1씩 증가, if else 또는 함수 호출 같은 명령어 만나면 점프할 주소로 동적 변경
- if 운영체제가 없다면
	- 프로그램 적재할 메모리 영역 선택
	- 레지스터 초기화 및 함수 진입점 찾아 PC 레지스터 설정
	- 외부 디바이스 사용시 드라이버 직접 연결
	- 멀티 태스킹 지원 불가 등
	- 직접 구현해야되는 내용이 복잡하고 번거롭다.
- 멀티 태스킹 구현을 위해 프로세스 간 전환 작업 필요 -> 프로세스의 상태 정보 저장하고 복구할 때 사용할 구조체 정의 필요
	```c
	struct *** {
		context ctx; // CPU 상황 정보 저장
	}
	```
- 운영체제는 시스템의 환경(프로세스 개수, CPU 개수, 메모리 용량)에 상관없이 프로그램이 CPU와 메모리를 독점하는 일관된 방식으로 동작할 수 있도록 지원
- 다중 프로세스: 독립적인 프로세스 간의 실행 결과 통신 및 전달
	- 프로세스 생성 시 오버헤드
	- 프로세스마다 주소 공간이 다르기 때문에 프로세스간 통신 복잡
- 다중 스레드: 하나의 프로세스 내 여러 개의 실행 흐름
	- 가볍고 생성 속도가 빠른 경량 프로세스
	- 스레드들 같은 주소공간에 속해있어 프로세스 간 통신 불필요
	- 다중 스레드가 공유 리소스 접근 시 동기화 문제: 상호 배제와 동기화 사용하여 명시적 해결(운영체제 지원 X)
- 스택: 함수 실행 시 필요한 정보(매개변수, 지역변수, 반환 주소)등을 저장
- 스레드 작업 분류
	- 긴 작업
		- 긴 시간이 소요되는 작업(디스크 저장)
		- 스레드 생성(요청당 스레드 request per thread)하여 처리
	- 짧은 작업
		- 짧은 시간이 소요(네트워크, 쿼리), 다량
		- 요청 당 스레드 생성시 다수의 스레드 생성과 전환에 많은 리소스와 부담 -> 스레드 풀
	- 스레드 풀
		- 스레드 여러 개 미리 생성하여 재사용
		- 생성과 종료 작업이 빈번하게 발생 안함
		- 생산자-소비자 패턴: 생산자(작업 전달) - 소비자(작업 처리)
		![[Pasted image 20241124004451.png]]
		- 스레드 풀에 전달되는 작업
		```c
		struct task {
			void* data; // 작업이 처리할 데이터
			handler handle // 데이터 처리 함수
		}
		```
		- 소비자는 작업 대기열에서 블로킹 상태로 대기 -> 생산자가 대기열에 작업 등록 ->  대기열에서 작업 꺼내서 처리함수 실행 
	- CPU 집약 작업
		- 외부 입출력에 의존할 필요없이 처리할 수 있는 작업(과학, 행렬 연산)
		- 코어 수와 동일한 만큼의 스레드 생성
	- 입출력 집약 작업
		- 연산 보다는 디스크 입출력이나 네트워크 입출력에 더 소비하는 작업
		- N(core) * (1 + WT(입출력 대기) / CT(연산))만큼의 스레드
##### 스레드 간 공유되는 프로세스 리소스
![](https://www.cs.uic.edu/~jbell/CourseNotes/OperatingSystems/images/Chapter4/4_01_ThreadDiagram.jpg)
- 스레드: 진입 함수에서 실행을 시작하여 생성된 하나의 실행 흐름
- 스택 프레임: 함수의 실행 시간 정보(반환값, 매개변수, 지역변수, 레지스터 정보) 저장
- thread context: 스레드의 현재 실행 상태(PC레지스터에 저장된 다음 명령어 주소, 스택 상단 위치를 가리키는 스택 포인터, 내부 레지스터 값과 스택)
- 코드 영역
	- 컴파일 한 이후 생성된 기계 명령어
	- 어떤 함수든지 모두 스레드에 적재하여 실행
	- 읽기 전용 영역이기에 thread safe
- 데이터 영역: 전역 변수
- 힙 영역: 동적으로 malloc이나 new 명령으로 할당되는 메모리 영역
- 스택 영역: 스레드 간에 논리적으로는 분리 / 물리적으로 접근 가능
- 그외 공유 가능 영역: 동적 라브러리의 코드와 데이터, 외부 파일 정보
- 스레드 전용 저장소(thread local storage)
	- 모든 스레드에서 접근할 수 있는 변수 저장
	- 변수의 인스턴스는 각 스레드에 속함
	```c
	__thread int a = 1; // 스레드 전용 저장소
	```
##### 스레드 안전 코드는 도대체 어떻게 작성해야 할까?
- 스레드 안전
	- 스레드 몇 개를 어떤 순서로 호출되든 상관없이 일관된 결과를 보장하는 코드
	- 전용 리소스를 사용하거나, 다른 스레드에 영향을 주지 않도록 대기 제약 조건에 맞게 공유 리소스를 사용하면 스레드 안전 달성 가능
- 스레드 사용 자원 구분
	- 스레드 전용 리소스: 지역 변수, 스택, 스레드 전용 저장소
	- 공유 리소스: 힙/데이터/코드 영역
- 공유 리소스 최소화: 전역 변수 -> 스레드 전용 저장소, 읽기 전용 여부 확인 
- 원자성 연산 
- 상호 배제: 프로그래머가 공유 리소스 접근 제어(뮤텍스, 스핀락, 세마포어)
##### 프로그래머는 코루틴을 어떻게 이해해야 할까?
- 코루틴
	- 시스템 영역: 주기적으로 타이머 인터럽트 발생, 운영체제가 스레드 일시 중지 여부 결정
	- 사용자 상태: 코루틴의 yield 예약어를 통해 프로그래머가 일시 중지 시점 명시적으로 지정, 스케줄링 제어권 획득
	- 코루틴의 스택 프레임 정보(상태 정보)는 힙 영역에 저장
	- 프로그래머의 동기 방식으로 비동기 프로그래밍 가능
##### 콜백 함수를 철저하게 이해한다
- 콜백: 함수의 변수화
	- 다른 코드에 매개변수로 전달되는 실행 가능한 코드
	- 동기
		- 함수를 호출한 스레드에서 호출된 함수의 반환까지 처리
		```java
		res = request();
		handle(res);
		```
	- 비동기
		- 함수를 호출한 스레드가 아닌 다른 스레드, 프로세스, 시스템에서 반환 값 처리
	```java
	request(handle);
	```
	- 콜백 함수는 무엇을, 콜백함수를 전달받는 모듈은 언제 콜백을 호출할지 결정
	- 비즈니스 로직이 복잡해질 경우 비동기 콜백 방식으로 작성하다보면 콜백 지옥에 빠질 수 있다.
##### 동기와 비동기를 철저하게 이해한다
- 동기 호출
	- 호출자와 피호출자 간에 종속, 피호출자의 반환전까지 기다림
	- 블로킹: 호출자와 피호출자가 다른 스레드에서 실행(파일 입출력)
- 비동기 호출
	- 호출자와 피호출자 간에 무관, 피호출자의 작업 완료되기 까지 기다리지 않음(논블록킹)
	- 호출자가 실행결과를 전혀 신경 쓰지 않을때: 콜백함수가 실행되는 다른 스레드 프로세스에서 처리
	- 호출자가 실행 결과를 반드시 알아야 할 때: 완료 알림을 받은 호출 스레드에서 결과 처리

##### 높은 동시성과 고성능을 갖춘 서버 구현
- 다중 프로세스(process-per connection)
	- 장점:
		- 간단한 구현
		- 격리된 프로세스 주소 공간으로 하나의 프로세스에 문제가 발생해도 영향 X
		- 다중 코어 리소스의 활용
	- 단점:
		- 프로세스 간 통신 어려움
		- 프로세스 생성과 종료의 부담
- 다중 스레드
	- 장점
		- 프로세스 주소 공간을 공유, 스레드간 별도의 통신 방식 필요 없음
		- 생성과 종료의 적은 부담
	- 단점:
		- 스레드 문제 발생 시 같은 프로세스를 공유하는 모든 스레드, 프로세스 강제 종료
		- 공유 데이터에 동시 접근 시 스레드 안전 문제 발생(상호 배제와 같은 동기화 필요)
- 초당 수만개 이상 요청 처리 시 요청당 스레드 생성 시 성능 문제 발생 가능
- 이벤트 기반 프로그래밍
	- 이벤트 도착시 이벤트 유형 확인 후 대응되는 이벤트 핸들러 호출하는 방식
	- 이벤트 순환: 발생하는 이벤트를 반복문을 사용하여 반복적으로 처리
- 이벤트 소스와 입출력 다중화
	- 파일 서술자: 유닉스 운영체제에서는 모든 것이 파일, 파일 서술자로 입출력 작업 실행
	- 입출력 다중화: 운영체제에 이벤트 발생 모니터링 위임
	```linux
	epoll_fd = epoll_create();
	//서술자를 epoll이 처리하도록 지정
	Epoll_ctr(epoll_fd, fd1, fd2, ...);
	while(1) {
		int n = epoll_wait(epoll_fd);
		// for ... event 처리
	}
	```
	- 입출력 다중화 이벤트 순환의 엔진이 되어 지속적으로 다양한 이벤트 제공
- 이벤트 순환과 다중 스레드
	- 단일 스레드: 모든 요청이 순차적으로 처리(요청 처리에 CPU 시간을 많이 소모한다면 응답이 느려짐)
	- 반응자 패턴: 이벤트 순환 스레드와 독립적인 작업자 스레드 생성/이벤트 순환 간단한 처리 후 작업자 스레드에 분배
	- 입출력 작업: 논블록킹(이벤트 순환에서 직접 호출 가능) / 블록킹(작업자 스레드)
- 서버 간 원격 프로시저 호출을 통해 통신(블록킹 호출) -> 더많은 스레드를 생성하기에는 리소스 낭비 -> 비동기 호출 -> 콜백안에 콜백 (콜백 지옥)
- 코루틴
	- 이벤트 순환에서 요청 받은 후 구현한 handler 함수 코루틴에 담아 스케쥴링과 실행을 위해 작업자 스레드에 배포
	- 네트워크 데이터 전송, RPC 통신 시작할 때 yield로 제어권 반환 -> 코루틴 일시 중지 -> 작업자 스레드 준비 완료된 다른 코루틴 실행

##### 메모리의 본질, 포인터와 참조
- 바이트(8비트): 정보를 나타내는 단위, 메모리 내 주소 보유(주소 지정)

##### 스택 영역: 함수 호출은 어떻게 구현될까?
- 함수 호출이 후입선출 순서로 진행되어 스택과 같은 데이터 구조로 처리에 적합
- 스택 프레임: 함수 실행 정보 저장
	- 반환 주소: 호출된 함수 반환  작업 이후 돌아갈 주소, 호출할 함수의 주소로 이동하기 전에 저장
	- 매개 변수, 반환값, 지역변수: 레지스터에 저장, 레지스터 수 부족할 경우 스택프레임에 저장
	- 초기 레지스터값: 레지스터 사용 전 초기값 스택프레임에 저장 후 함수 실행 완료 시 복원
##### 힙 영역: 메모리의 동적 할당은 어떻게 구현될까?
- 힙 영역: 동적인 메모리 할당과 해제가 가능한 영역
- 메모리 할당 상태 추적: 연결 리스트(헤더(메모리 조각 크기,할당 여부) + 페이로드)
- 할당 전략
	- 최초 적합: 가장 먼저 발견된 요구 사항 만족하는 항목 반환
		- 메모리 할당 과정에서 앞부분에 작은 메모리 조각이 많이 존재 -> 더 많은 탐색시간
	- 다음 적합: 여유 메모리 마지막 발견 위치에서부터 검색 시작
	- 최적 적합: 여유 메모리 모두 탐색하여 할당가능한 최소 여유 메모리 영역 선택
- 해제 전략
	- 해제 후 즉시 병합 / 연기 후 병합: 인접한 메모리 할당 여부 파악을 위해 메모리 구조 변경(헤더 + 페이로드 + 푸터)
##### 메모리를 할당할  때 저수준 계층에서 일어나는 일
- 커널 모드: 운영체제 코드 시행
- 유저 모드: 일반적인 어플리케이션 코드 실행(메모리, 기계 명령어 수행 제한)
![](https://www.cs.csustan.edu/~john/Classes/CS3750/Notes/Chap01/1_13modeTranstn.jpg)
- 표준 라이브러리: 사용자 상태에서 실행되어 실행 중인 운영체제에 따라 대응되는 시스템 호출을 선택
- 메모리 할당
	- malloc 호출시 여유 메모리 조각 탐색 및 할당
	- brk 같은 시스템 호출로 힙 영역 확장
	- 시스템 호출 시 운영체제의 가상 메모리 시스템이 힙 영역 확장(실제 물리 메모리 할당 X)
	- malloc이 사용자 상태에서 메모리 조각 반환
	- 해당 메모리 공간 접근 시 시스템 내부적으로 page fault 발생. 가상과 물리메모리 매핑 및 할당
##### 고성능 서버의 메모리 풀은 어떻게 구현될까?
- malloc(범용적, 표준 라이브러리 영역) / 메모리풀(한정적, 응용 프로그램 영역)
- 메모리 풀: 한 번에 큰 메모리 조각 요청 후 그 위에서 자체적으로 할당 및 해체를 관리
	- 여러 크기 메모리 할당
		- 여유 메모리 조각 추적을 위해 연결리스트로 메모리 조각 연결
		- 이전 메모리 조각 크기의 2배에 달하는 여유 공간 생성 후 할당
	- 스레드 안전: 스레드 전용 저장소 활용
##### 대표적인 메모리 관련 버그
- 지역 변수의 포인터 반환: 함수 호출 이후 유효하지 않음
- 포인터 연산의 잘못된 이해: 가리키는 자료형 만큼 이동
- 문제 있는 포인터 역참조하기: 잘못된 주소(코드, 읽기 전용 영역인 경우: 강제종료/ 다른 영역의 경우: 다른 메모리 영역 침해)
- 초기화 되지 않은 메모리 읽기: 여유 메모리 조각을 반환할 경우 초기화되지 않을 수 있음
##### 왜 SSD는 메모리로 사용할 수 없을까?
- 주소 지정 단위: 메모리(바이트) / SSD(조각)
- 가상 메모리의 제한 : 32비트 시스템의 최대 주소 지정 범위 4GB
- SSD 사용 수명 문제: 기록 가능한 최대 바이트(TBW) 이상 기록시 병목 현상 발생

##### CPU는 유휴 상태일 때 무엇을 할까?
- 프로세스 스케줄링: 대기열(큐)로 프로세스 관리, 프로세스 우선순위에 따라 관리
![](https://user-images.githubusercontent.com/25416425/145781067-b8ccad2d-06c4-4810-9b3b-77831f16f30e.png)
- 대기열이 비어있다면(준비 완료 상태인 프로세스 존재X), 유휴 프로세스 실행
- 유휴 프로세스: 절전 상태로 전환하는 halt 명령어 무한 루프, 인터럽트 발생 시 중단 후 준비 완료 프로세스 존재 확인
##### CPU는 숫자를 어떻게 인식할까?
- 최상위 비트가 정수 부호 결정: 0(양수), 1(음수)

| 표현    | -0  | 덧셈 역원 연산   |
| ----- | --- | ---------- |
| 부호-크기 | 존재  | -0 반환      |
| 1의 보수 | 존재  | -0 반환      |
| 2의 보수 | 없음  | 0(오버플로) 반환 |
- CPU는 인간이 이해하는 추상적인 개념 이해 X, 인간이 설계한대로 동작할 뿐

##### CPU가 if문을 만났을 때
- 파이프라인: 기계 명령어 처리 과정 세분화(인출, 해독, 실행, 쓰기) 각 단계별 별도의 하드웨어로 처리
- 조건부 점프 명령: 실행이 완료되기 전까지 후속 명령어 주소를 알 수 없음 -> 분기 예측
- likely/unlikely 매크로: 컴파일러에 더 가능성 높은 분기 제공

##### CPU 코어 수와 스레드 수 사이의 관계는 무엇일까?
- 코어: 명령어 실행 하드웨어 / 스레드: 명령어 실행 흐름의 단위(소프트웨어)
- 다중 코어: CPU / IO Bound 프로세스에 따라 적절한 개수의 스레드 할당

##### CPU 진화론(상): 복잡 명령어 집합의 탄생
- 프로그램: 명령어의  집합(CPU 관점)
- 명령어 집합: CPU가 실행 가능한 명령어의 모음
- 초창기 어셈블리어로 작성된 대부분의 프로그램 -> 풍부한 기능의 명령어 집합으로 프로그램 작성 편리성 도모
- 의미상 간격: 기계 명령어와 고급 언어 개념간 차이를 줄여 더 적은 코드로 많은 작업 가능
- 폰 노이만 구조: 컴퓨터 저장 장치에 프로그램과 사용 데이터 저장, 코드 데이터 자체도 메모리 공간 점유![](https://upload.wikimedia.org/wikipedia/commons/thumb/e/e5/Von_Neumann_Architecture.svg/510px-Von_Neumann_Architecture.svg.png)
- 직접 연결 방식의 명령어 집합: 명령어 집합 변경에 유연한 대응 불가(CPU 설계, 디버깅 복잡)
- CPU 내부에서 복잡한 명령어를 더 간단한 명령어(마이크로코드)으로 변환하여 설계 단순화
- 마이크로코드 자체의 문제: 디버깅 복잡, 많은 트랜지스터 소모

##### CPU 진화론(중): 축소 명령어 집합의 탄생
- 메모리와 컴파일러 성능의 발전: 더이상 어셈블리어로 코드를 작성하지 않음
- 파레토의 법칙: 전체 실행시간의 80% 동안 명령어집합의 20% 정도만 활용, 컴파일러 또한 단순 명령어로 변환하려는 경향이 있음
- 마이크로 코드의 버그로 인한 성능 저하: 기계 명령어를 생성하는 컴파일러로 해결 불가
- 축소 명령어 집합
	- 명령어 자체의 복잡성: 컴파일러 출력 기계 명령어의 CPU 제어능력 향상
	- 컴파일러: CPU는 더 많은 세부사항을 컴파일러에 제공
	- LOAD/STORE 구조: 복잡 명령어 집합과 달리 메모리 접근 전용 명령어 사용
- 복잡 명령어 집합/ 축소 명령어 집합
```
MULT A B //고급 언어와 유사, 최소한의 코드로 작업 수행 및 코드가 차지하는 공간 절약

LOAD RA, A
LOAD RB, B
PROD RA, RB
STORE A, RA
```
- 축소 명령어 집합의 명령어 실행 시간 거의 일정: 파이프라인 기술 적용 용이(처리량 증가)

##### CPU 진화론(하): 절체절명의 위기에서 반격
- 인터페이스(명령어 집합)은 그대로 유지한 채, 내부 구현(명령어 실행 방식) 변경
- 복잡한 명령어를 간단한 명령어(마이크로 명령어)의 집합으로 변환
- 하이퍼스레딩: 하나의 코어가 두 개의 코어로 보이게 하는 추상화 기술, 병렬 처리 명령어 증가
- 복잡 명령어 집합의 우세한 규모의 생태계 기반 성장 서버 시장 지배, 단순 명령어 집합 모바일 시장에서 유리한 위치 선점
##### CPU, 스택과 함수 호출, 시스템 호출, 스레드 전환 ,인터럽트 처리 통달하기
- 레지스터: 메모리에 비해 접근 속도 빠르지만 용량에 한계, 프로그램 실행 시 메모리에 저장, CPU 사용 시 임시로 레지스터에 데이터 보관
- 스택 포인터: 스택 상단을 가리키는 레지스터, 함수 호출 스택 추적 가능
- 명령어 주소 레지스터: 다음에 실행할 명령어 주소를 가지는 레지스터(순차적 증가/조건 분기)
- 상태 레지스터: CPU 동작 상태값(오버플로우, 자리올림수, 커널/유저모드 등) 정보 저장
- 프로그램 실행 시 상황정보를 저장 복원: 함수 호출/시스템 호출/스레드 전환/인터럽트 처리
- 커털 상태 스택: 운영체제가 시스템 호출 완료하는데 필요한 실행 시간 스택, 사용자 상태 스레드에 대응되는 커널 상태 스택 존재
	- 사용자 상태에서 프로그램 실행
	- 시스템 호출에 대응되는 기계 명령어 호출
	- CPU 상태 전환(커널모드)
	- 대응되는 커널 실행 스택 탐색 후 사용자 상태 스레드의 실행 상황 정보 저장
	- 일반적인 함수 호출 방식으로 커널실행 상태 스택에 저장
	- 저장된 사용자 상태 스레드 상황 정보 복원 및 실행
- 인터럽트: 현재 CPU 실행 흐름을 끊고 인터럽트 서비스 루틴 실행 후 실행하던 프로그램 복원을 위한 실행 시간 스택 필요(커널 상태 스택 / 인터럽트 서비스 루틴 스택이라는 별도의 스택 할당)
- 스레드 전환
	- 시스템 내부 타이머가 인터럽트 신호 발생
	- 현재 스레드 일시 중지, 커널 상태 전환
	- 타이머 인터럽트 처리 프로그램(현재 스레드에 할당된 남은 시간 조각 파악) 실행
	- 스레드 전환(주소 공간 전환, 상황정보 저장 및 복원)

##### 캐시, 어디에나 존재하는 것
- 캐시: CPU와 메모리 사이 급격한 속도 차이 보완
- L1, L2, L3, 메모리 순으로 접근, 속도 저하 발생
![](https://w3.cs.jmu.edu/kirkpams/OpenCSF/Books/csf/html/_images/CSF-Images.9.1.png)
- 메모리-캐시 간 데이터 불일치
	- 연속 기입(write-through): 캐시 업데이트 시 메모리도 같이 업데이트
	- 후기입(write-back): 캐시 업데이트가 아닌 제거 시점에 메모리 갱신
- 다중 코어 캐시 간의 일관성
	- MESI protocol: 캐시의 데이터에 수정,배타,공유,무효 네가지 상태 부여하여 일관성 관리하는 프로토콜
	- 변수 접근시 다른 코어의 캐시에도 있는지 확인 후 해당 캐시에도 갱신
- 여유 메모리 공간을 활용하여 디스크의 데이터 캐시
- 디스크는 메모리의 창고: 새로운 프로세스에 할당할 수 있는 여유 메모리 공간이 없을 경우, 자주 접근하지 않는 공간을 디스크에 기록 후 해제
- 주소 체계(논리->물리) 변환 -> 캐시(l1,l2,l3) 확인 -> 메모리 -> 디스크 공간에 있던 프로세스 메모리에 적재 후 반환
- 분산 파일 시스템:
	- 로컬디스크는 원격의 분산 파일 시스템에서 네트워크로 전송된 파일 저장, 캐시 역할 수행
	- 메세지 미들웨어인 카프카를 활용하여 원격 분산 파일 시스템의 데이터를 데이터 흐름 형태로 직접 로컬 컴퓨터 시스템의 메모리로 끌어 올 수 있음
##### 어떻게 캐시 친화적인 프로그램을 작성할까?
- 프로그램 지역성의 원칙: 메모리의 규칙적인 접근 원칙
	- 시간적 지역성: 프로그램이 메모리 조각을 접근한 이후 여러 번 참조
	- 공간적 지역성: 접근하는 메모리 조각의 인접한 메모리 조각을 참조
- 메모리 풀: 연속적인 메모리 공간 내 요청과 할당이 이루어져 공간적 지역성이 우수
- 캐시 친화적인 프로그램 작성 기법
```c
bool find(struct List* list, int target) {
	while (list) {
		if (list->value == target) {
		return true;
		}
		list = list->next;
	}
	return false;
}
// 데이터 구조 재배치
struct List {
	List* next;
	int value; //공간적 지역성 개선을 위해 자주 접근하는 변수는 서로 가까운 위치에 선언
	int arr[SIZE];
}
// 콜드, 핫 데이터의 분리
struct Arr {
	int arr[SIZE]; //자주 접근하는 데이터(핫) / 접근하지 않는 데이터(콜드) 분리하여 더 나은 지역성 개선
}
```
- 캐시 친화적 자료구조 사용: vector O, list(연결 리스트: 공간 지역성 낮음) X
- 2차원 배열의 경우 행 우선 방식이 열 우선 방식보다 캐시 친화적

##### 다중 스레드 성능 방해자
- 캐시 라인: 캐시와 메모리 상호작용의 기본 단위(64바이트)
- 캐시 튕김 문제
```c
atomic<int> a;

void threadf() {
	for (int i = 0; i < 500000000000000; i++) {
		++a;
	}
}

void run() {
	thread t1 = new thread(threadf);
	thread t2 = new thread(threadf);
	t1.join();
	t2.join();
}

void run() {
	for (int i = 0; i < 500000000000000; i++) {
		++a;
	}
}
```
- 각각의 스레드들이 할당된 코어 안 캐시들의 일관성을 보장하기 위한 작업 필요
- 캐시 튕김: 데이터 갱신 시 동일한 데이터가 저장된 캐시들에 대해 무효화
- 거짓 공유 문제
```c
struct data {
	int a;
	int b;
}
struct data global_data;
// 위 예시에서 a 대신 global_data의 a , b 동시 접근
```
- 각각의 스레드들은 어떤 변수도 공유하지 않지만 각각의 스레드가 접근하는 변수들은 동일한 캐시 라인에 있을 가능성이 높음 -> 캐시 튕김 문제 발생

##### 봉화희제후와 메모리 장벽
##### 명령어의 비순차적 실행: 컴파일러와 OoOE
- 기계 명령어를 생성하는 단계: 컴파일 중에 명령어 재정렬
- CPU가 명령어를 실행하는 단계: 실행 중에 명령어가 비순차적으로 실행
```c
int a;
int b;

void main() {
	a = b + 100;
	b = 200;
}
```
- 컴파일 시 명령어 재정렬: b = 200 코드가 먼저 실행(초기값은 별도의 레지스터 저장)
- 명령어의 비순차적 실행
	- 기계 명령어 인출
	- 명령어를 대기열에 넣고 명령어에 필요한 피연산자 입력
	- 명령어는 대기열에서 피연산자 준비 완료까지 대기, 준비된 명령어 먼저 실행
	- 실행 결과를 대기열에 입력
	- 이전 명령어의 실행 결과 기록될 때까지 대기 후 실행 결과 기록
- 명령어가 의존하는 피연산자를 기다리는 동안 파이프라인 내 빈 슬롯 존재 -> 비순차적으로 명령어 실행
- 저장 버퍼
	- 일부 시스템의 경우 캐시의 갱신 시 일관성 유지를 위해 대기열 시스템 도입
	- 기록 작업 시 대기열에 직접 기록
	- CPU는 캐시 갱신 기다리지 않고 명령어 계속 실행
- 기록 작업은 비동기: CPU는 실제 캐시와 메모리를 갱신할 때까지 기다리지 않고 계속 다음 명령어 실행
- 비순차적 실행은 자기 자신 이외에 또 다른 코어가 해당 코어를 바라볼 때, 특히 공유 데이터를 바라볼 때만 나타나는 현상(단일 스레드에서는 관찰 불가)
- 잠금 없는 프로그래밍
	- 프로그래밍 언어 차원에서 잠금 활용한 공유 리소스 동기화 문제 해결
	- 잠금을 통한 보호를 사용하지 않는 상태에서 다중 스레드의 공유 리소스 처리
	- 비교와 교환과 같은 원자성 보장되는 작업 사용
```c
bool is_enemy_coming = false;
int enemy_num = 0;

void thread_zhouyouwang() {
	enemy_num = 1000000;
	is_enemy_coming = true;
}
void thread_zhuhou() {
	int n;
	if(is_enemy_coming) {
		n = enemy_num;
	}
}
```
- 메모리 장벽: 특정 스레드의 비순차적 명령 실행을 방지하는 기계 명령어
	- 특정 코어가 명령어를 실행하는 순서, 다른 코어에서 보이는 순서가 코드 순서와 일치하도록 보장
	- LoadLoad: Load 명령어를 실행할 때 다음에 오는 Load 명령어가 먼저 실행되는 것을 방지(ex. is_enemy_coming 변수 읽기 전 enemy_num 초기값 조회)
	- StoreStore: Store 명령어 실행 전 다음 Store 명령어 먼저 실행되는 것을 방지(enemy_num, is_enemy_coming 변수 초기화 순서 보장)
	- LoadStore: Load 명령어가 캐시 미스나면 일부 CPU에서는 다음에 오는 Store 명령어가 먼저 실행될 수 있음
	- StoreLoad: 쓰기 작업이 모든 다른 코어에서 확인되기 전까지 다음에 오는 읽기 작업 미리 실행 불가능, 해당 장벽 이후 시점에는 최신값 보장
	- StoreStore: 갱신 순서 유지, 최신값 보장 불가\
- 획득-해제 의미론
	- 획득 의미론: 뒤에 있는 모든 메모리 작업은 Load 작업 이전에 실행 불가(LoadLoad LoadStore)
	- 해제 의미론: 앞에 있는 모든 메모리 작업은 Store작업 이후에 실행 불가(StoreStore, LoadStore)
```c++
std::atomic<bool> is_enemy_coming(false);
int enemy_num = 0;

void thread_zhopuyouwang() {
	enemy_num = 1000000;
	//해제 장벽
	std::atomic_thread_fence(std::memory_order_release);
	// memory_order_relaxed 옵션: 원자성 확보하는 선에서 매모리 재정렬 허용
	is_enemy_coming.store(true, std::memory_order_relaxed);
}

void thread_zhuhou() {
	int n;
	if(is_enemy_coming.load(std::memory_order_relaxed)) {
		// 획득 장벽
		std::atomic_thread_fence(std::memory_order_acquire);
		n = enemy_num;
	}
}
```
- CPU 종류별 명령어 재정렬: 약한 메모리 모델(거의 모든 유형의 재정렬), 강한 메모리 모델(StoreLoad 재정렬)
- 잠금: 스레드 간 공유 리소스 보호
- 잠금 사용 프로그래밍
	- 코드가 임계 영역 내에서 실행되는 것을 보장하여 명령어 재정렬 문제 자동 처리
	- 잠금을 유지하는 프로세스 중단시 잠금 요청 스레드도 같이 블로킹
	- 잠금 요청 스레드는 대기 상태 혹은 순환대기(스핀락)
	- 임계영역이 커지지 않도록 주의, 상호 배제로 상황 정보 전환 부담 증가 주의
- 잠금 없는 프로그래밍"
	- 명령어 재정렬 문제 고려 필요
	- 운영체제의 스레드 스케줄링과 무관하게 명령어 재정렬하여 실행가능 스레드 확보
	- 복잡한 리소스 경쟁 문제로 복잡한 코드 구현 난이도

##### CPU는 어떻게 입출력 작업을 처리할까?
- 장치 레지스터: 데이터 레지스터 / 제어, 상태 정보 레지스터
- 입출력 기계 명령어: 장치 레지스터를 읽고 쓰는 특정 명령어(x86의 IN, OUT)
	- 장치 레지스터별 고유한 주소 부여, 하드웨어 회로가 장치 레지스터 식별
- 메모리 사상 입출력: 메모리를 읽고 쓰는 것처럼 장치를 제어
	- 주소 공간 일부분을 장치에 할당
- 장치 상태 검사: 장치 상태 레지스터 값 확인
	- 폴링: 장치 상태 레지스터를 지속적으로 읽는 작업 반복(동기)
	- 인터럽트 구동식 입출력: 장치에서 하드웨어 인터럽트 발생(비동기)
- 인터럽트 구동식 입출력
	- 처리 방식: 현재 실행 중인 프로그램과 인터럽트 간 우선 순위 비교, 우선 순위 높은 것을 실행
	- 함수 호출: 단일 스레드(흐름)안에서 존재하기에 호출전 반환 주소, 범용 레지스터값, 매개변수 등의 정보 저장
	- 인터럽트: 서로 다른 두 실행 흐름 포함하므로 함수 호출에 비해 저장할 정보들이 많음
- 프로그램 실행 상태 스택
	- 상태가 먼저 저장될수록 상태 복원은 더 나중에 진행
	- 커널 영역에 존재
	- 다음 처리할 명령어 주소를 비롯한 프로그램 실행 상태 정보 저장
##### 디스크가 입출력을 처리할 때 CPU가 하는 일은 무엇일까?
- 장치 제어기: 자신만의 버퍼와 레지스터에 데이터 저장 가능, 장치 드라이버의 명령을 받아 외부 장치 제어하는 하드웨어
- 장치 드라이버: 장치 제어기를 동작하기 위한 운영체제에 속한 코드
- 직접 메모리 접근
	- CPU는 DMA에 입출력 작업 명령: 작업 종류, 메모리 위치, 장치 레지스터 종류 등 작업 정보 전달
	- 시스템 버스 사용 권한 획득 후 입출력 작업 수행
	- 입출력 작업 완료 후 CPU에 인터럽트 발생
- 가상 메모리 지원: DMA 컨트롤러에 물리 메모리, 가상 주소의 사상 정보 제공
- 캐시 메모리 일관성: 입출력 데이터에 상응하는 캐시 데이터를 즉시 메모리 갱신
- CPU와 디스크 입출력 작업은 독립적(비동기 방식)으로 실행
##### 파일을 읽을 때 프로그램에는 어떤 일이 발생할까?
- 메모리 관점에서의 입출력은 데이터 복사
```c
char buffer[LEN];
read(buffer);
```
- 입출력 실행 프로세스는 블로킹 상태로 전환되면서 블록킹 대기열에 저장
- DMA는 장치에서 메모리로 데이터 복사 / CPU는 준비 완료 대기열에 있는 다른 프로세스 실행
- 입출력 완료 시 인터럽트 발생, 인터럽트 감지한 운영체제는 입출력 실행한 프로세스를 블록킹 대기열에서 준비 완료 대기열로 이동
- 타이머 인터럽트 발생 후 기존 프로세스로 전환
- zero-copy: 일반적으로 입출력 데이터는 운영체제를 경유하여 입출력 진행, 운영체제를 우회하여 직접 데이터를 프로세스 주소 공간에 복사하는 작업
##### 높은 동시성의 비결: 입출력 다중화
- Unix 운영체제에서는 모든 것(디스크, 터미널, 파이프)이 파일
- 파일 입출력 작업 인터페이스로 외부 장치 접근 가능
- 파일 서술자: 파일을 식별하기 위한 번호, 프로세스가 사용할 정보(저장 위치, 포인터 등 나머지 정보는 운영체제가 대신 처리)
```c
int conn_fd = accept(...);
if (read(sockect_fd1, buff) > 0) {}
if (read(sockect_fd2, buff) > 0) {}
// 블록킹 입출력: 이전 입출력 작업 모두 완료될 때까지 대기
```
- 요청별 별도의 스레드 생성: 많은 스레드 생성, 스케줄링과 전환에 많은 부담
- 입출력 다중화
	- 파일 서술자 획득
	- 특정 함수를 호출하여 커널에게 파일 서술자를 감시하다 읽거나 쓸 수 있는 파일 서술자 나타날 때 반환하라는 메세지 전달
	- 함수 반환되면 읽고 쓸 수 있는 조건의 준비된 파일 서술자 획득
	- select: 최대 1024개의 파일 서술자 감시 가능
		- 호출 시 블록킹, 파일 서술자 중 하나라도 읽기 쓰기 가능 이벤트 발생 시 다시 실행 재개
		- 어떤 파일 서술자가 준비되었는지 모든 파일 서술자 확인
	- poll: 파일 서술자 개수 제한 해제, 이벤트 종류 세밀하게 지정
	- epoll: 이벤트 발생한 파일 서술자만 준비 완료 목록에 추가 후 반환
