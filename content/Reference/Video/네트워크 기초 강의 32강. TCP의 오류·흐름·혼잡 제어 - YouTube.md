# TCP의 3가지 핵심 신뢰성 기능: 오류, 흐름, 혼잡 제어 완전 정복

## Introduction: TCP, The Reliable Delivery Service

컴퓨터 네트워크의 세계에서 TCP(Transmission Control Protocol)는 꼼꼼하고 신뢰할 수 있는 우편 서비스와 같습니다. [00:10]() 이 서비스는 단순히 소포를 보내는 데 그치지 않고, 모든 소포가 손상 없이, 올바른 순서대로, 빠짐없이 목적지에 도착하도록 보장합니다. 인터넷을 통해 파일을 전송하고, 웹 페이지를 로딩하고, 이메일을 보내는 등의 모든 작업이 안정적으로 이루어지는 것은 바로 TCP의 이러한 신뢰성 덕분입니다.

이 문서에서는 TCP를 이토록 신뢰할 수 있게 만드는 세 가지 핵심 메커니즘을 명확하게 파헤쳐 봅니다. [00:43]()

* **오류 제어 (Error Control):** 데이터가 손실되거나 순서가 뒤바뀌었을 때 대처하는 방법
* **흐름 제어 (Flow Control):** 수신자가 감당할 수 있는 속도로 데이터를 조절하는 방법
* **혼잡 제어 (Congestion Control):** 네트워크 전체가 마비되지 않도록 전송량을 조절하는 방법

## 1\. 오류 제어 (Error Control): 데이터가 길을 잃었을 때

### 체크섬만으로는 부족한 이유

TCP 헤더의 **체크섬(Checksum)** 필드는 데이터가 전송 중에 손상되었는지는 감지할 수 있습니다. [01:35]() 하지만 패킷이 아예 유실되거나, 순서가 뒤바뀌어 도착하거나, 중복으로 도착하는 문제까지는 해결하지 못합니다. [01:53]() 완벽한 신뢰성을 보장하기 위해서는 이러한 문제들을 감지하고 해결할 수 있는 더 정교한 방법이 필요합니다.

### 오류 감지 신호

TCP는 크게 두 가지 신호를 통해 데이터 전송에 문제가 발생했음을 인지합니다. [02:30]()

1.  **타임아웃 발생 (Timeout):** 송신자가 데이터를 보낸 후, 정해진 시간 내에 그에 대한 확인 응답(ACK)을 받지 못하는 상황입니다. [02:41]() 이는 데이터가 중간에 사라졌을 가능성이 높다는 신호입니다.
2.  **중복된 확인 응답 (Duplicate ACKs) 수신:** 수신자가 특정 순서의 데이터를 받지 못하면, 마지막으로 제대로 받은 데이터에 대한 확인 응답을 반복해서 보냅니다. [02:50]() 송신자가 동일한 ACK를 여러 번 받으면, 특정 데이터가 유실되었음을 짐작할 수 있습니다. [03:40]()

### 해결책: ARQ (자동 재전송 요구)

TCP는 위와 같이 오류를 감지했을 때 **ARQ (Automatic Repeat reQuest, 자동 재전송 요구)** 라는 전략을 사용합니다. [05:03]() 이는 문제를 진단하고 유실된 데이터를 자동으로 재전송하여 데이터의 완전한 전달을 보장하는 프로토콜입니다. [05:16]() ARQ에는 세 가지 주요 방식이 있습니다.

#### 1.1. 스톱 앤 웨이트 (Stop-and-Wait) ARQ: 하나씩, 차근차근

가장 단순한 방식으로, 한 번에 하나의 데이터(세그먼트)를 보내고 그에 대한 확인 응답(ACK)을 받아야만 다음 데이터를 보내는 방식입니다. [06:03]()

이 방식은 구조가 매우 단순하고 신뢰성이 높다는 장점이 있지만, ACK를 기다리는 동안 네트워크를 사용하지 못하므로 네트워크 이용 효율이 심각하게 저하된다는 치명적인 단점이 있습니다. [06:49]()

#### 1.2. 고백 N (Go-Back-N) ARQ: 문제가 생긴 곳부터 전부 다시

스톱 앤 웨이트의 비효율을 해결하기 위해 **파이프라이닝(Pipelining)** 개념이 도입되었습니다. [07:43]() 이는 ACK를 기다리지 않고 여러 개의 세그먼트를 연속해서 보내는 기술입니다.

고백 N 방식은 파이프라이닝을 사용하되, 만약 중간에 데이터 하나(예: N+2번)가 유실되면, 그 시점부터 뒤에 보낸 모든 데이터(N+2, N+3, N+4...)를 전부 재전송합니다. [08:35]() 예를 들어 수신자가 N+3, N+4번 세그먼트를 정상적으로 수신했더라도, N+2번이 없으면 이들을 모두 폐기하고 송신자가 N+2번부터 다시 보내주기를 기다립니다. [09:08]() 이 방식은 **누적 확인 응답(Cumulative ACKs)** 을 사용합니다. [09:28]()

#### 1.3. 선택적 재전송 (Selective Repeat) ARQ: 필요한 것만 콕 집어 다시

고백 N보다 한 단계 더 발전한 효율적인 방식입니다. 이 방식은 문제가 발생한 데이터만 선택적으로 재전송합니다. [11:31]() 예를 들어 N+2번 데이터만 유실되었다면, 다른 데이터는 그대로 두고 정확히 N+2번 데이터만 다시 보내는 것입니다.

이 방식은 **개별 확인 응답(Individual ACKs)** 을 사용하며, [12:21]() 불필요한 재전송을 최소화하여 가장 효율적입니다. 오늘날 대부분의 시스템이 이 방식을 채택하고 있습니다. [12:31]()

### ARQ 방식 비교 요약

| 재전송 방식 | 핵심 동작 | 장점/단점 |
| :--- | :--- | :--- |
| **Stop-and-Wait ARQ** | 하나 보내고, 응답 받을 때까지 대기 | 장점: 단순함.<br>단점: 네트워크 효율 매우 낮음. [06:49]() |
| **Go-Back-N ARQ** | 오류 발생 지점부터 모든 데이터를 재전송 | 장점: 파이프라이닝으로 효율 개선.<br>단점: 불필요한 재전송 발생. |
| **Selective Repeat ARQ** | 오류가 발생한 데이터만 선택적으로 재전송 | 장점: 가장 효율적인 재전송.<br>단점: 구현이 상대적으로 복잡함. |

### 핵심 최적화: 빠른 재전송 (Fast Retransmit)

TCP는 타임아웃이 발생할 때까지 무작정 기다리지 않습니다. 만약 송신자가 동일한 데이터에 대한 **중복 ACK를 3번 수신**하면, 타임아웃 시간이 다 되기 전이라도 '아, 이 데이터가 유실되었구나'라고 판단하고 즉시 해당 데이터를 재전송합니다. [10:26]() 이 스마트한 최적화 덕분에 오류 복구 속도가 훨씬 빨라집니다.

오류 제어를 통해 각 데이터 조각이 정확히 전달됨을 보장했다면, 이제는 데이터를 너무 빨리 보내 수신자를 압도하지 않도록 전송 '속도'를 조절하는 흐름 제어에 대해 알아보겠습니다.

## 2\. 흐름 제어 (Flow Control): '너무 빨라요\!' 외침에 귀 기울이기

### 핵심 개념과 비유

흐름 제어의 목적은 간단합니다. 송신자가 수신자가 처리할 수 있는 속도보다 더 빠르게 데이터를 보내지 못하도록 막는 것입니다. [13:54]() 깔때기에 물을 부을 때 너무 빨리 부으면 물이 넘쳐흐르는 것과 같습니다. 네트워크에서는 이 '넘쳐흐름'이 바로 수신 측에서의 데이터 유실로 이어집니다. [13:28]()

### 해결책: 슬라이딩 윈도우 (Sliding Window)

TCP는 이 문제를 해결하기 위해 **슬라이딩 윈도우(Sliding Window)** 프로토콜을 사용합니다. [14:43]()

* **윈도우(Window)** 란 송신자가 확인 응답(ACK)을 받지 않고도 한 번에 보낼 수 있는 데이터의 최대량을 의미합니다. [15:14]()
* 이 과정에서 두 가지 핵심적인 윈도우가 사용됩니다: **수신 윈도우 (Receive Window)** 와 **송신 윈도우 (Send Window)**.

흐름 제어는 다음과 같은 동적인 과정으로 이루어집니다.

1.  수신자는 자신이 현재 처리할 수 있는 데이터 공간(버퍼 크기)의 양, 즉 **수신 윈도우 크기**를 TCP 헤더에 담아 송신자에게 계속해서 알립니다. [17:15]()
2.  송신자는 이 정보를 받아 자신의 **송신 윈도우 크기**를 조절합니다. [17:34]() 이때 송신 윈도우의 크기는 수신자가 광고한 수신 윈도우 크기를 절대 초과할 수 없습니다 (**송신 윈도우 \<= 수신 윈도우**).
3.  수신자가 데이터를 처리하고 수신된 세그먼트에 대한 ACK를 보내면, 송신자 윈도우의 앞쪽 경계가 앞으로 **"슬라이딩"** 하며 이동합니다. [16:40]() 이를 통해 이전에 윈도우 밖에 있던 새로운 데이터 세그먼트를 전송할 공간이 열리게 됩니다.

흐름 제어가 송신자와 수신자 '둘 사이'의 속도 문제를 해결한다면, 네트워크 '전체'의 교통 체증을 관리하는 더 큰 차원의 제어, 바로 혼잡 제어는 어떻게 동작할까요?

## 3\. 혼잡 제어 (Congestion Control): '도로가 꽉 막혔어요\!' 상황 대처하기

### 혼잡이란 무엇인가?

네트워크 **혼잡(Congestion)** 은 여러 대의 컴퓨터가 하나의 공유기를 통해 인터넷을 주고받을 때 인터넷이 느려지는 상황과 같습니다. [18:28]() 너무 많은 기기가 동시에 하나의 라우터나 회선을 통해 데이터를 보내려고 하면 패킷 처리가 지연되거나 아예 버려지는(drop) 현상이 발생합니다. [18:46]() 이 상황이 악화되면 재전송이 재전송을 낳아 네트워크 전체가 마비되는 **혼잡 붕괴(Congestion Collapse)** 상태에 이를 수 있습니다. [19:16]()

### 흐름 제어 vs. 혼잡 제어

학생들이 자주 혼동하는 두 개념의 차이점은 다음과 같습니다. [19:46]()

| 구분 | 흐름 제어 (Flow Control) | 혼잡 제어 (Congestion Control) |
| :--- | :--- | :--- |
| **목적** | 수신자의 처리 속도 보호 | 네트워크 전체의 과부하 방지 |
| **주체** | 수신자가 자신의 상태를 송신자에게 알림 [20:00]() | 송신자가 네트워크 상태를 스스로 판단하여 조절 [20:09]() |
| **고려 대상** | 1:1 통신에서의 수신자 버퍼 | 나와 목적지 사이의 모든 네트워크 장비 |

### 혼잡 윈도우 (Congestion Window, cwnd)

혼잡 제어를 위해 송신자는 **혼잡 윈도우(Congestion Window, cwnd)** 라는 값을 스스로 유지합니다. [20:20]() 이 값은 네트워크에 혼잡을 일으키지 않고 안전하게 보낼 수 있는 데이터의 양을 나타냅니다. [20:30]() **cwnd**는 송신자가 자체적으로 계산하고 관리하는 값으로, TCP 헤더에는 포함되지 않습니다. [21:20]()

### 현대 TCP의 혼잡 제어 알고리즘: 단계별 여정

현대의 TCP는 네트워크 상황에 맞춰 **cwnd**를 동적으로 조절하는 정교한 다단계 알고리즘을 사용합니다.

1.  **느린 시작 (Slow Start): 출발은 지수적으로 빠르게** [24:47]()
    * 이름과 달리, 이 단계의 목표는 초기에 네트워크의 가용 대역폭을 빠르게 찾아내는 것입니다. **cwnd**는 1에서 시작하여 매 **RTT(Round Trip Time)** 마다 2배씩 지수적으로 증가합니다. [25:09]()
    * **종료 조건:** **cwnd**가 특정 임계값(느린 시작 임계치)에 도달하거나, 패킷 손실이 감지되면 이 단계는 종료됩니다. [26:07]()
2.  **혼잡 회피 (Congestion Avoidance): 조심스럽게 속도 올리기** [27:10]()
    * 느린 시작 임계치에 도달한 후, TCP는 더 신중한 모드로 전환합니다. **cwnd**는 매 RTT마다 1씩 선형적으로 증가합니다. [27:20]()
    * **목표:** 네트워크에 부담을 주지 않으면서 조심스럽게 추가 대역폭을 탐색하는 것입니다. 이것이 **AIMD(Additive Increase/Multiplicative Decrease)** 의 **'합 증가(Additive Increase)'** 부분입니다. [22:12]() 이 단계는 네트워크의 현재 한계 용량에 근접했다고 판단하고, 과부하를 유발하지 않기 위해 보수적으로 대역폭을 탐색하는 단계입니다.
3.  **혼잡 감지 및 대응: 문제 발생\!**
    * 혼잡이 감지되면 TCP는 즉각적으로 전송량을 줄입니다. [23:45]() 대응 방식은 혼잡의 심각도에 따라 다릅니다. TCP는 3개의 중복 ACK 수신을 '가벼운 혼잡'으로, 타임아웃 발생을 '심각한 혼잡'으로 간주합니다. [28:36]() 3개의 중복 ACK는 특정 패킷 하나만 유실되었을 뿐 데이터와 ACK는 여전히 오가고 있다는 긍정적인 신호인 반면, 타임아웃은 ACK조차 돌아오지 않을 정도로 네트워크 상황이 좋지 않다는 훨씬 심각한 신호이기 때문입니다.
    * **A. 가벼운 혼잡 (3개의 중복 ACK 수신):**
        * **대응:**
            * **빠른 재전송(Fast Retransmit)** 을 통해 유실된 패킷을 즉시 재전송합니다. [10:26]()
            * **빠른 회복(Fast Recovery)** 을 시작합니다. [28:24]() **cwnd**를 1로 리셋하는 대신, 절반으로 줄이고 즉시 혼잡 회피 단계로 진입합니다. [29:33]() 이는 전송 속도를 더 빠르게 회복하기 위함입니다.
    * **B. 심각한 혼잡 (타임아웃 발생):** [28:45]()
        * **대응:**
            * 느린 시작 임계치를 현재 **cwnd**의 절반으로 줄입니다.
            * **cwnd**를 1로 완전히 초기화합니다.
            * 느린 시작 단계부터 다시 시작합니다. [30:41]() 이것이 AIMD의 **'곱 감소(Multiplicative Decrease)'** 부분입니다. [22:12]()

이처럼 TCP는 네트워크 상황에 맞춰 공격적으로 속도를 올리고, 문제가 감지되면 보수적으로 속도를 줄이는 정교한 춤을 추며 안정적인 통신을 유지합니다.

## Conclusion: The Symphony of Reliability

TCP의 세 가지 제어 메커니즘은 신뢰성 있는 데이터 전송이라는 하나의 목표를 위해 조화롭게 연주하는 오케스트라와 같습니다. [31:02]()

* **오류 제어**는 연주 중 발생한 작은 실수를 즉시 바로잡고,
* **흐름 제어**는 연주자가 청중(수신자)이 감당할 수 있는 속도로 연주하도록 조절하며,
* **혼잡 제어**는 공연장(네트워크) 전체가 불협화음으로 무너지는 것을 막기 위해 전체적인 연주 강도를 조절합니다.

이 세 가지 기능이 함께 작동하기에, 우리는 본질적으로 신뢰할 수 없는 인터넷이라는 거대한 무대 위에서 파일 전송, 웹 브라우징과 같은 안정적인 애플리케이션을 매일같이 사용할 수 있는 것입니다.
